# Архитектура: обзор

- Версия: 1.1 (стек C + Raylib)
- Связанные документы: [Требования](../requirements.md) · [Модули](modules.md) · [Процесс](engineering.md)

## 1. Ключевой принцип: чистое ядро

Вся игровая логика (правила, движение, столкновения, еда, счёт, скорость) —
**чистое ядро на C без raylib**, без файлов, таймеров и системных вызовов. Ядро:

1. получает состояние игры и вход (буфер направлений),
2. возвращает новое состояние и список событий (`ATE`, `DIED`, `TURNED`),
3. источник случайности — собственный ГПСЧ (xorshift) с сидом, живущим
   в состоянии: никакого `rand()`/`srand()` — только детерминизм.

**Почему:** юнит-тесты без окна и графики (NFR-3), воспроизведение любого бага
по сиду, ядро можно собрать и прогнать на любой платформе вообще без raylib.

## 2. Слои

```
┌─────────────────────────────────────────────┐
│ app (main.c)     raylib-окно, game loop,    │
│                 связывание слоёв            │
├─────────────────────────────────────────────┤
│ input            raylib-события клавиатуры →│
│                 буфер направлений           │
├─────────────────────────────────────────────┤
│ core            ЧИСТАЯ ЛОГИКА: поле,        │
│                 змейка, еда, правила, счёт  │
├─────────────────────────────────────────────┤
│ render          отрисовка GameState через   │
│                 raylib (только чтение)      │
├─────────────────────────────────────────────┤
│ storage         файл рекордов (обёртка с    │
│                 fallback на %APPDATA%)      │
└─────────────────────────────────────────────┘
```

Правила зависимостей (стрелки только вниз):

- `core` не включает `raylib.h` и ничего о внешнем мире не знает —
  компилируется и тестируется без окна.
- `input` и `storage` используют типы `core`, но не наоборот.
- `render` читает состояние и никогда не мутирует его.
- `app/main.c` — единственное место, связывающее всё вместе.

## 3. Игровой цикл

Свой цикл в `main.c` поверх raylib (`WindowShouldClose` / `BeginDrawing`):

```c
while (!WindowShouldClose()) {
    input_poll(...);              // собрать ввод в буфер
    accumulator += GetFrameTime();
    while (accumulator >= state->tick_interval_ms / 1000.0) {
        tick(state, input_next_direction());  // fixed timestep
        accumulator -= state->tick_interval_ms / 1000.0;
    }
    render_draw(state);           // рисуем столько раз, сколько позволяет FPS
}
```

- **Fixed timestep:** логика тикает с фиксированным интервалом (клетка за тик),
  рендер — каждый кадр raylib. Накопитель времени: на медленном железе логика
  «догоняет», на быстром — не ускоряется.
- Скорость игры меняется только интервалом тика (FR-11), а не шагом движения.
- raylib не навязывает структуру цикла — контроль наш, это часть «хардкора».

## 4. Состояние и память

Один `GameState` (поле, змейка, еда, направление, счёт, статус, интервал тика,
сид ГПСЧ). Правила владения:

- Изменяется только функцией `tick` в core.
- Змейка — динамический массив `Point*` + длина/ёмкость, владелец — `GameState`;
  создание/уничтожение через `game_create` / `game_destroy` (no leaks, NFR-7
  и риск из requirements §7).

## 5. Расширяемость (не-цели v1, но заложить)

| Расширение       | Как ложится на архитектуру                              |
| ---------------- | ------------------------------------------------------- |
| Бонусная еда     | новая сущность в `core` + отрисовка; контракт `tick` не меняется |
| Препятствия/уровни | массив `walls[]` в состоянии, те же правила коллизий  |
| Звук             | raylib audio по событиям `GameEvent`                   |
| Linux/macOS порт | заменить пути `storage/` и пресет сборки; core не меняется |

## 6. Технические решения (ADR)

- **ADR-001 — C11 + `-Wall -Wextra -Wpedantic -Werror`.** В C компилятор —
  первая линия обороны; ноль предупреждений держим с первого дня, чинить потом
  дороже (NFR-7).
- **ADR-002 — Raylib, а не SDL/сырой WinAPI.** Змейке не нужен менеджер
  сущностей (движок не нужен), но нужны окно, рендер и шрифты — без бойлерплейта.
  Raylib — C99-библиотека из ~100 функций, официальный пример змейки в
  комплекте, ставится через pacman. SDL3 дал бы хардкора больше, но треть
  кода была бы бойлерплейтом.
- **ADR-003 — CMake + Ninja.** Стандарт сборки C/C++; пресеты (`CMakePresets.json`)
  скрывают разницу MinGW/MSVC/Linux; Ninja — мгновенные инкрементальные сборки.
- **ADR-004 — Unity + CTest для тестов.** Unity — два файла на чистом C,
  FetchContent без внешних зависимостей; CTest интегрирует прогоны в
  стандартный `ctest`. Логика core тестируется без raylib и окна.
- **ADR-005 — Рекорды в файле за обёрткой `storage/`.** Прямо рядом с бинарником
  при наличии права записи, fallback — `%APPDATA%/snake/`; обёртка тестируется
  и не роняет игру при недоступном диске.
- **ADR-006 — Свой ГПСЧ (xorshift) в состоянии ядра.** `rand()` глобален и
  недетерминирован между платформами; сид в `GameState` даёт воспроизводимость
  тестов и багов (NFR-3).
