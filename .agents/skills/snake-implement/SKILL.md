# Реализация фич «Змейки» (C + Raylib)

## Порядок работы

1. Прочитай `docs/requirements.md` и найди FR/NFR, к которому относится задача.
   Если задача не покрыта существующим требованием — сначала допиши новый FR
   (со следующим свободным номером) и согласуй формулировку с пользователем,
   потом код.
2. Прочитай `docs/architecture/modules.md`, раздел «Куда класть новый код» —
   определи модуль. Если изменение никуда не ложится, не клади мимо правил:
   подними вопрос о пересмотре архитектуры.
3. Напиши тест на желаемое поведение в `tests/core_tests.c` (Unity). Тест красный.
4. Минимальная реализация. Тест зелёный.
5. Проверь себя по списку правил ниже и закоммить:
   `feat(core): FR-7 рост змейки при поедании` (формат — в
   `docs/architecture/engineering.md`).

## Правила, которые нельзя нарушать

- `src/core/` — чистая логика: без `raylib.h`, файлов, системных вызовов,
  таймеров и `rand()`. Случайность — только через xorshift-ГПСЧ с сидом
  в `GameState`: детерминизм нужен для тестов и воспроизведения багов по сиду.
- Единственная точка изменения `GameState` — функция `tick` в `core`.
  Рендер и ввод никогда не мутируют состояние (рендер получает `const`).
- Все числа игры (скорости, очки, размеры поля) — в `src/config.h` и приходят
  в ядро через `GameConfig`. В `core/` нет «магических чисел».
- Память: всё, что выделил `game_create`, освобождает `game_destroy`;
  новые аллокации в core — только с продуманным владельцем и освобождением.
- Side effects (окно, ввод, файлы) — только в `input/`, `storage/`, `render/`
  и `main.c`.
- `core/` не включает ничего вне `core/`.

## После реализации

Собери и прогони тесты: `cmake --build build && ctest --test-dir build`
(или скилл `snake-verify`). Коммитить только зелёную сборку с нулём
предупреждений компилятора (`-Werror` включён — грязный код просто не соберётся):
`main` всегда зелёная. Если менялось поведение игры — в коммите должен быть
ID требования.
